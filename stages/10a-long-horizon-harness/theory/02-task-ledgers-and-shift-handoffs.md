# 02 — Task ledgers and shift handoffs

A task ledger externalizes progress so each model session can start from current project truth rather than full historical dialogue.

Minimal task state:

```text
id
description
status
attempts
latest note
artifact paths
```

## Persist before work

Tiny-Agent marks a task `running` and saves before calling the worker. This makes the transition visible if the worker crashes.

After execution it stores:

```text
completed / failed
note
artifacts
new tasks
```

## Recover a task left `running`

A process can die after persisting `running` but before persisting the terminal result. On a new runtime, `TaskLedger.recover_interrupted()` makes that ambiguity explicit:

```text
running from dead worker
-> pending
-> note: recovered_interrupted_task
-> next attempt
```

This restores liveness, **not exactly-once execution**. The previous worker may have completed an external side effect immediately before dying. Therefore replayable long-horizon tasks must use Stage 06/07/10 idempotency, approval, transaction, or downstream deduplication rules appropriate to the action.

## Handoff summary

The next session usually needs:

- objective;
- status counts;
- recent notes;
- current task;
- relevant artifacts/files.

It usually does **not** need every token generated by every previous worker.

`LongHorizonHarness.handoff_summary()` therefore emits a compact derived view and explicitly tells the worker to use workspace/ledger state as the source of continuity.

## Failed vs pending vs abandoned

Do not collapse every non-completed task into “try again.” A failed task may need:

- repair;
- human review;
- a new plan;
- dependency resolution;
- permanent stop.

Production ledgers normally need richer states/leases/ownership than the teaching implementation, but explicit state and explicit crash ambiguity are the first requirements.
